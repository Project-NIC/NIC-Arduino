# NIC-MLA — спецификация формата

*[English](DESIGN-MLA.md) · [Čeština](DESIGN-MLA_cs.md) · [Русский](DESIGN-MLA_ru.md)*

*Основной является английская версия.*

> **Статус:** v1.2 — **финальная** · **Дата:** 2026-10-03
> **MLA** = *Matroshka Logging Archive* — универсальный однофайловый контейнер
> (данные + лог в одном файле, как Matroska / tar / DriveSpace).
>
> Этот документ определяет формат v1.2 — финальную версию NIC-MLA. **Состояние реализации:** эталонная реализация на Python
> (`nic_mla.py`, `nic_mla_archive.py`, `tools/mla_schema.py`) и библиотеки на C
> (`c/` — только запись для ATmega + полная для ARM/PC) готовы и
> побайтно идентичны (проверено перекрёстным тестом совместимости C↔Python).
>
> **Принцип проектирования — «глупый» контейнер.** MLA только хранит байты: 16-байтную
> запись лога, покрытую CRC, + блок данных, а также две самоописывающие таблицы в
> префиксе (имена/единицы полей и индекс станции → реальный номер). Всё «умное»
> — сжатие, шифрование, перевод номеров станций, транспорт — находится в
> отдельном слое glue.

## 1. Назначение и область применения

NIC-MLA — это **универсальный контейнер для записи данных** с измерительных станций
(метеостанция, электросчётчик, …). Цель — один переносимый файл, который несёт
**данные и лог вместе** и читается на разных платформах.

**Зачем он нужен:** покончить с бардаком из миллиона форматов. Вместо груды файлов и
инструментов → **одна таблица**, в которую можно «запихнуть» что угодно. Вынимаешь карту из
устройства, вставляешь в компьютер, и **один тривиальный просмотрщик** собирает структуру
из внутренних регистров, описанных настолько хорошо, что справится даже ребёнок.
Цель — не быть «навороченным», цель — **простой, интуитивный и тривиальный процесс**,
который экономит время и деньги. (То, что отдельные части этого подхода существуют где-то ещё, неважно —
ценность в том, что они **собраны вместе и самоописываемы.**).

### Целевые платформы и роли

| Платформа | Роль | Что делает |
|---|---|---|
| **ATmega328** (8-bit) | **WRITE-ONLY** | только дописывает записи (append) с интервалом ~15 мин; никакого поиска или редактирования на чипе |
| Arduino 32/64-bit, STM, ESP | запись + при необходимости чтение | как ATmega + локальное чтение |
| **Хост** (PC / Raspberry) | чтение, поиск, редактирование | загружает весь лог в RAM, фильтрует, экспортирует |

**Ключевой принцип:** запись тривиальна и надёжна (из-за ATmega), а весь интеллект (поиск, запросы, редактирование) работает на хосте, где лог целиком загружается в RAM. **На диске НЕТ дерева/AVL — только плоский лог**, который хост просматривает последовательно. Поля лога спроектированы так, чтобы эта фильтрация была быстрой (время, индекс станции, тип).

### Вне области применения

- **Редактирование записей** → отдельный проект просмотрщика *Volkov Data Ecosystem* (NIC-VDE).
- **Сжатие** → опционально, выполняется **отдельным методом**; контейнер лишь
  **помечает** сжатые данные (один бит `compressed` + расстояние `kf_back`), сам он
  сжатие не определяет (см. §4).
- **Прямой доступ к «сырой» SPI-NOR/NAND** → **экспериментально и заморожено** (см.
  `experimental/`). Целевой носитель — **SD/флеш-карта**: собственный контроллер карты
  обеспечивает выравнивание износа, ECC и переназначение. Мы отказались от «сырой» NOR из-за риска блокировки некоторых чипов при записи неполных страниц/блоков и из-за зависимости от производителя. Симулятор NOR остался лишь как доказательство универсальности формата (ядро не зависит от носителя благодаря HAL), а не как поддерживаемый путь.

## 2. Структура файла

Мы сохраняем проверенную физическую модель — **два потока, растущие навстречу друг другу**
в файле фиксированного размера:

```
offset 0                                                              EOF
┌────────────┬───────────────┬──────────┬─────────────┬──────────────┐
│ PREFIX     │ DATA stream → │ free 0xFF │ ← LOG stream │ PREFIX mirror│
│ 1–255 sec  │ (grows up)    │           │ (grows down) │ (copy)       │
└────────────┴───────────────┴──────────┴─────────────┴──────────────┘
             ▲ data_base      ▲ top_ptr  bot_ptr ▲ region_end
```

- **DATA** растёт вверх от `data_base` (`top_ptr` = куда пойдёт следующий блок).
- **LOG** растёт вниз от `region_end` (`bot_ptr`; следующая запись ложится
  по адресу `bot_ptr − log_rec_size`).
- Между ними — свободное пространство, заполненное `0xFF`.
- **PREFIX** по умолчанию занимает один сектор 512 B; он только растёт (целыми секторами, до
  255), когда таблицы SCHEMA + STATION не помещаются. `data_base` = размер префикса.
- **Зеркало PREFIX**: побайтно идентичная копия префикса в
  последних (размер префикса) байтах файла, чтобы один плохой сектор по смещению 0 не мог
  «ослепить» весь файл — `mount()` переключается на неё. Поэтому поток LOG
  заканчивается на `region_end = file_size − prefix size`, сразу под зеркалом.
  Отдельной области индекса нет — дерева поиска на диске нет вовсе.

### Почему фиксированный, заранее выделенный размер

Файл **целиком выделяется заранее** при `format()` и заполняется `0xFF` (точно так же, как сегодняшний
`MlaPosixHAL.create`). На FAT/SD это правильный выбор:

- цепочка кластеров FAT выделяется заранее → файл не растёт и не фрагментируется,
- все **логические смещения остаются стабильными** на протяжении всей жизни файла,
- модель «два указателя навстречу друг другу» укладывается в фиксированную область без конфликтов с ФС.

### Условие «заполнен»

```
top_ptr + next_block_size  >  bot_ptr − log_rec_size
```

### Режимы заполнения (`container_kind` в префиксе)

| Значение | Режим | Поведение | Рекомендация |
|---|---|---|---|
| 0 | **Жёсткая остановка** | RuntimeError при заполнении | просто |
| 1 | **Ротация файлов** | при заполнении открывается следующий файл `NIC0001.MLA`, `NIC0002.MLA`, … ; каждый префикс несёт `file_seq` | **рекомендуется для FAT/SD** |
| 2 | **Кольцевой буфер** | DATA переходит обратно в начало, самый старый сектор освобождается (`sector_erase`), а соответствующие слоты LOG помечаются как отброшенные | только RAW/NOR / эксперимент |

Предпочтительна ротация: каждый файл монтируется независимо и устойчив к сбоям,
карты огромны, так что заполнение случается редко. Кольцевой буфер усложняет восстановление и
отложен (см. §9).

### Решение: размер контейнера и предварительное выделение

- **Свободное пространство = `0xFF`** (как у свежей NOR после стирания) остаётся — **без суперблока**.
  Это проще всего для MCU: чип просто пишет, а `mount()` находит границу,
  просматривая в поисках `0xFF`. Никакого сохранения указателей в префиксе.
- **Размер контейнера по умолчанию ~1 MB.** Предварительное выделение 1 MB (заполнение `0xFF`) на MCU —
  быстрая одноразовая операция; для больших объёмов **ротируйте несколько файлов по 1 MB**.
- **Большие файловые системы** = много файлов по 1 MB на огромной карте. **Агрегацию и чтение
  через несколько файлов выполняет PC** (`MlaArchive`) — мощный процессор «переваривает всё»,
  поэтому более медленное предварительное выделение и полный просмотр не проблема. MCU держит открытым
  только один файл 1 MB.
- 32-битная адресация → один файл максимум **4 GB**; выше этого (и ниже) — ротация.
  Если вас смущает количество файлов, можно увеличить `file_size` (например, 16–64 MB) —
  это просто выбор в `format()`.

## 3. Префикс (1–255 секторов по 512 B)

Префикс — это структурированный заголовок 34 B, за которым следуют две самоописывающие таблицы
(SCHEMA + STATION), а в конце — CRC16 по всему предшествующему. Обычно он
занимает **один сектор 512 B**; если таблицы не помещаются, он растёт целыми секторами по 512 B
(до **255 ≈ 127 KB**), и CRC переносится в последние 2 байта префикса.

> Предел в 255 секторов — жёсткий потолок, а не цель: он существует лишь потому, что
> счётчик занимает один байт. **Рекомендуемый максимум — 16 секторов (8 KB)**; с
> автоматически подбираемыми по размеру таблицами SCHEMA/STATION реальная станция к нему и близко не подходит.

```
[0]   magic[4]        b"MLA\0"
[4]   version         1 B   = 1
[5]   cluster_shift   1 B   8=256B · 10=1KB · 12=4KB · … · 15=32KB
[6]   log_rec_size    1 B   = 16
[7]   flags           1 B   CRC mode (bits 0-1): 0=NONE · 1=DATA · 2=FULL
[8]   file_size       4 B   uint32 LE
[12]  reserved        8 B   0
[20]  container_kind  1 B   0=single · 1=rotation
[21]  file_seq        2 B   uint16 LE  file order in rotation
[23]  keyframe_intv   1 B   keyframe interval for compression (default 0 = N/A)
[24]  enc_caps        1 B   bitmask of encodings this file may carry
[25]  data_base       4 B   uint32 LE  = prefix size (first DATA byte)
[29]  region_end      4 B   uint32 LE  = file_size − prefix size (LOG stream end;
                                         a mirror copy of the prefix follows it)
[33]  reserved        1 B   0
[34]  SCHEMA table    …     §3.1
[..]  STATION table   …     §3.2
[end-2] mla_crc16         2 B   LE  — over everything before it
```

> **Зарезервировано, не реализовано (досылка через uplink).** Зарезервированные 8 B по адресу **[12]** предназначались
> для `first_ts` (4 B, Unix-секунды первой записи LOG в файле) + `last_ts` (4 B, проставляется при
> ротации/закрытии), чтобы uplink с промежуточным хранением (store-and-forward) мог выбрать нужный файл ротации
> только по заголовку. v1.2 финальна и этого не содержит: v1.2 записывает [12] = 0, а читатель проверяет
> первую запись LOG каждого файла.

### 3.1 Таблица SCHEMA — имена/единицы полей для CSV/SQL

Создаётся/читается `tools/mla_schema.py`. Позволяет любому читателю экспортировать записи в CSV/SQL
**без предварительных знаний** — станция несёт собственное описание столбцов.

```
[0] tbl_ver  1 B  = 1 (MLA_SCHEMA_VER)
[1] n_log    1 B  number of LOG fields (describe the timestamp etc.)
[2] n_data   1 B  number of DATA fields (the packed payload columns)
[3 ..]       (n_log + n_data) × 16 B field descriptors:
   width 1 B · unit 1 B · exp10 1 B (i8) · flags 1 B (bit0=signed) ·
   offset 2 B (i16 LE) · mantissa 2 B (i16 LE, user scale numerator, 0 ≡ 1) ·
   name 8 B (UTF-8, NUL-padded)
   physical = (raw + offset) × mantissa × 10^exp10
```

Словарь единиц универсален (общий для всей спецификации); от устройства зависит только *состав*
полей (какие датчики, масштаб, ширина, **имя из 8 символов**), и он передаётся
в файле.

### 3.2 Таблица STATION — индекс → реальная станция

```
[0] sta_ver  1 B  = 0x53
[1] n        1 B  number of stations (1..255)
[2 ..]       n × 42 B records (index i in the log → record i-1), each:
                identity(8 B)  + elevation(2 B, i16 LE, metres, 0x8000 = unknown)
                + name(32 B, UTF-8, NUL-padded, all-zero = none)
```

8-байтная **идентичность непрозрачна для MLA** — формируйте её теми же кодировщиками, что
использует формат datalogger (`dl_gps` = 2× i32 deg×1e7, `dl_ident` = region/number/
kind/reserved как 4× u16, или `dl_raw` = 8 байт как есть). Это **унифицирует**
идентичность станции на 8-байтной модели; старая 6-байтная запись region/number/reserved
**выведена из употребления**. `elevation` — отдельное поле в метрах со знаком (i16 LE,
`0x8000` = неизвестно), не входящее в непрозрачную идентичность. `name` — отдельная
человекочитаемая метка фиксированной длины 32 байта (UTF-8, дополнение NUL, все нули = нет) —
материал для StationXML `<Site><Name>`; это метаданные, записываемые **один раз в префиксе**, они НЕ передаются
в каждой 16-байтной записи лога. Люди назначают номера станций с пропусками — glue
отображает их в компактные 1-байтные индексы и обратно.

> **«Глупый» контейнер.** Обе таблицы записываются как есть, полученные сверху, и никогда
> не интерпретируются в пути C/MCU. Сжатие, шифрование, перевод номеров станций
> и транспорт находятся в отдельном слое glue.

## 4. Флаг сжатия (без реестра типов)

### 4.1 Один бит, а не байт типа

v1.2 **не** содержит байта `rec_type`/класса (measure / event /
config / delta / keyframe / …). Файлы **однородны** — что *означает* полезная нагрузка
(какой байт — температура, какой — влажность), берётся из **таблицы
SCHEMA** (§3.1), а не из метки типа в каждой записи. Метка типа, зависящая от glue,
устаревает и портится; SCHEMA — нет.

Вместо этого запись LOG несёт только байт `flags` (§5):

- **бит 7 — `compressed`**: полезная нагрузка — это блоб кодека (например, NIC-DMD).
  Контейнер никогда не заглядывает внутрь; этот бит означает лишь «при чтении передай полезную нагрузку
  слою кодека».
- **биты 0–6 — `kf_back`**: для сжатого потока — на сколько записей назад находится
  соответствующий ключевой кадр (0 = эта запись **является** ключевым кадром). Полные 7 бит → 0..127,
  так что интервал ключевых кадров выбирает пишущая сторона/устройство, а читателю его никогда
  не нужно сообщать (ключевой кадр = `kf_back == 0`).

### 4.2 Какой кодек — указано в блоке данных, а не в записи

Формат **несёт** бит сжатия, но **не определяет метод**.
КАКОЙ кодек / ключевой кадр / вариант — закодировано в **собственном заголовке блока данных**
(NIC-DMD уже так делает: байт 0 блоба). Поэтому добавление нового кодека — это несколько
строк в glue, а контейнер никогда не меняется. Два уровня:

- **запись LOG** — это индекс: поиск/фильтрация (в том числе по биту `compressed`)
  без чтения данных;
- **блок DATA** — самоописывающий непрозрачный блоб:
  `MAGIC · [codec hdr 1–4 B][compressed data] · CRC`.

`keyframe_intv` (байт префикса 23) — лишь подсказка читателю: периодичность, которую пишущая сторона
*намеревается* соблюдать; по умолчанию 0. Он никогда не является определяющим; определяющим является `kf_back == 0`.

**Практический пример:**
1. Glue кодирует: отсчёт 0 = ключевой кадр (необработанная опорная точка), отсчёты 1..6 = дельты, отсчёт
   7 = снова ключевой кадр (периодичность DMD по умолчанию — 7).
2. Контейнер сохраняет каждый блоб с `compressed = 1` и `kf_back` = расстояние
   до ключевого кадра (0 на ключевых кадрах) — без интерпретации, только индексация.
3. При чтении декомпрессор (а не ядро) воспроизводит поток от ближайшей записи,
   у которой `kf_back == 0`.

### 4.3 Возможности кодирования (`enc_caps`)

Байт префикса 24 (`enc_caps`) — рудиментарная битовая маска-**подсказка** для читателя,
оставленная ради прямой совместимости; v1.2 по умолчанию оставляет его равным **0**. Он никогда не является
ограничением — определяющая информация о кодировании находится в собственном заголовке каждого блока данных,
поэтому читатель всегда должен обрабатывать блок по его собственным правилам.

## 5. Запись лога (16 байт)

Запись лога находится в потоке LOG (растущем вниз от `region_end`, то есть
сразу под хвостовым зеркалом префикса). Она имеет фиксированный размер
**16 байт**, и **вся запись покрыта CRC** — поля «flags вне CRC»
нет.

```
[0]  offset      4 B  uint32 LE  byte offset of the data block in DATA
[4]  timestamp   4 B  uint32 LE  Unix seconds (from the caller's RTC/GPS)
[8]  subsec      2 B  uint16 LE  two opaque bytes (0..65535); meaning owned by the glue, MLA assigns none
[10] length      2 B  uint16 LE  payload size (1..65535 B)
[12] flags       1 B  uint8      bit7 = compressed, bits0-6 = kf_back (records back
                                  to the owning keyframe; 0 = this record IS a keyframe)
[13] station     1 B  uint8      index 1..255 into the prefix station table (0 = none)
[14] mla_crc16       2 B  LE  — CRC16 over [0..13]
```

Почему 16 B: это степень двойки, поэтому запись никогда не пересекает границу сектора 512 B, а
адресация слотов — это сдвиг, а не умножение: самый удобный размер для MCU.
Поле `subsec` — два непрозрачных байта, которые контейнер только
переносит; MLA не придаёт им никакого смысла. Имя намеренно читается двояко:
доля **сек**унды (sub-**sec**ond) *и* под**сек**ция (sub-**sec**tion, например индекс ротации / секции).
Решает слой glue — он может использовать поле как одно 16-битное значение, как два независимых
байта или сразу для нескольких целей (например, старший байт = секция/ротация, младший байт
= субсекундный тик для дискретизации значительно выше 1 Hz). Если поле не используется, ставьте 0.
Единственный байт `flags` упаковывает бит `compressed` и расстояние `kf_back` (см. §4).

**Это позиция, а не полная метка времени.** Два байта содержат *индекс отсчёта* — 0..127
для канала 128/s, 0..8191 для канала 8192/s, — и везде, где частота является степенью двойки,
перенос этого индекса на более мелкую сетку — это сдвиг: нигде не хранится точная доля
секунды, и ничего не нужно делить, чтобы её прочитать. Вызывающая сторона, которой для субсекундной позиции нужно больше
16 бит, делит её на две части: грубая половина размещает запись здесь, тонкая едет
в полезной нагрузке — а для такого канала точный момент и так место именно там.

### 5.1 Состояния записи (без поля flags)

Слот интерпретируется исключительно по его байтам:

| Состояние | Байты | Как определяется |
|---|---|---|
| **Свободна** | все `0xFF` | свежий / стёртый носитель |
| **Действующая** | данные + совпадающая CRC | `mla_crc16(body) == stored CRC` |
| **Отброшена** | все `0x00` | CRC не сходится (обнулённое тело **не** даёт хеш `0x0000`) |

Отбросить запись = **перезаписать 16 B нулями**. Тогда её CRC больше не
совпадает, и все читатели её пропускают. Это заменяет старый трюк «переключить один байт flags
вне CRC» и позволяет покрыть контрольной суммой всю запись.

### 5.2 `station` — индекс, а не номер

`station` — это **1-байтный индекс** (1..255; 0 = нет) в таблице STATION в
префиксе (§3). Реальные номера станций/регионов — которые люди и инструменты назначают
как им угодно, с пропусками, — хранятся в этой таблице; контейнер никогда
не интерпретирует индекс. Перевод индекс ↔ реальный номер — задача glue на хосте.

> Никаких контрольных точек. Размер файла фиксирован, а лог имеет фиксированный шаг, поэтому
> `mount()` находит границу двоичным поиском и читает `offset + length` самой новой действительной
> записи, чтобы восстановить `top_ptr`, — сохранять нечего, поэтому записи
> контрольной точки не существует.

## 6. Блок данных (переменной длины)

Полезная нагрузка данных, записываемая в поток DATA:

```
[0]       magic       2 B  0xAB 0xCD  (sync word)
[2]       <payload>   N B  app data (1 to 65535 B)
[2+N]     mla_crc16       2 B  LE  — CRC16 over the payload (0xFFFF if CRC mode = NONE)
```

**Почему в блоке нет байта типа?** В v1.2 вообще нет типа у отдельной записи —
файлы однородны, а смысл берётся из SCHEMA, а не из метки. Благодаря этому
поток данных остаётся **полностью под управлением приложения**. Когда схема находится в префиксе, полезная нагрузка —
это столбцы датчиков, упакованные вплотную друг к другу (§3.1); `mla_decode_payload()` разделяет и
масштабирует их в `(name, unit, value)` для CSV/SQL.

## 7. Устойчивость к сбоям

Протокол — **сначала LOCK, потом DATA**:

1. **Оборванная запись блокировки** (прерывание во время записи LOG) → у этого слота
   неверная CRC → он пропускается при монтировании. Поиск границы двоичным поиском продолжается.
2. **Оборванная запись данных** (LOG в порядке, но блок данных неполон) → его `MAGIC`
   отсутствует → при монтировании блокировка **обнуляется** (все 16 B перезаписываются
   `0x00`, так что её CRC не сходится), а `top_ptr` возвращается к `rec.offset`.
3. **Отбрасывание** любой записи выполняется так же — перезаписью нулями; тогда CRC
   не сходится, и читатели её пропускают. Байта flags нет, и вне CRC ничего нет.
4. `recover()`: находит `MAGIC`, перебирает длины 1..65535, пока `CRC16(payload)`
   не совпадёт; восстановленные записи помечаются как несжатые (`compressed = 0`,
   `kf_back = 0`), поскольку кодирование невозможно восстановить только по блоку.
5. Никаких контрольных точек: размер файла фиксирован, а лог имеет фиксированный шаг, поэтому
   двоичный поиск плюс чтение самой новой записи напрямую восстанавливают состояние.
   Начинайте просмотр с крупным шагом (например, 256 или 2000 для большого файла) и
   отступайте на один назад, когда наткнётесь на `0xFF`, — на диске ничего не нужно чинить.

## 8. Настраиваемые параметры (задаются при `format()`, хранятся в префиксе)

| Параметр | Где | Варианты | По умолчанию |
|---|---|---|---|
| `cluster_shift` | байт 5 | 8…15 (256 B … 32 KB) | 12 (4 KB) |
| `flags` (CRC) | байт 7, биты 0-1 | NONE / DATA / FULL | FULL |
| `container_kind` | байт 20 | single / rotation | single |
| `file_seq` | байт 21 | 0…65535 | 0 |
| `keyframe_intv` | байт 23 | 0…255 | 0 |
| `enc_caps` | байт 24 | битовая маска кодирований | по назначению |
| `schema_table` | [34..) | из `tools/mla_schema.py` | пусто |
| `station_table` | после schema | из `tools/mla_schema.py` | пусто |

`log_rec_size` зафиксирован равным **16**, а `data_base` вычисляется (= размер префикса,
который равен 512 B, если таблицы не переполняются в дополнительные секторы).

## 9. Вне области применения (находится в слое glue, а не в MLA)

MLA — «глупый» контейнер; следующее намеренно **не** является его задачей:

- **Перевод номеров станций** — лог хранит 1-байтный индекс; его отображение
  в реальный номер станции, возможно с пропусками, — задача glue (через таблицу STATION,
  которую он записал).
- **Сжатие** — MLA его только помечает (бит `compressed`; `kf_back` связывает
  запись с её ключевым кадром, 0 = ключевой кадр). Кодек и его вариант — отдельно,
  они находятся в собственном заголовке блока данных.
- **Шифрование** — аналогично: отдельная библиотека; MLA хранит любые байты, которые получает.
- **Транспорт (LoRa / Wi-Fi / сеть)** — каждая запись самодостаточна
  (длина + CRC), поэтому «отправить запись» = отправить её байты. Транспорт —
  выбор glue.
- **Ротация файлов** по множеству файлов — платформенный glue поверх файловой системы
  (`MlaArchive` в Python); каждый файл монтируется независимо благодаря `file_seq`.
  Glue также может **называть каждый файл по его `first_ts`** (например, датой `YYYYMMDD`), чтобы
  листинг каталога служил наглядным временным индексом для догоняющей передачи store-and-forward. Это
  *только политика именования* — определяющими остаются `file_seq` и заголовок (включая зарезервированный слот `first_ts`),
  поскольку часы на момент создания могут быть не установлены (холодный старт до получения GPS), а FAT 8.3
  ограничивает короткие имена (тогда используйте имя по `file_seq` и при желании переименуйте файл, когда время станет известно).

Такое разделение делает MLA достаточно маленьким для ATmega (только запись, лог по 16 B, один
сектор префикса 512 B) и при этом позволяет мощному хосту построить поверх него сколь угодно
умную систему.
