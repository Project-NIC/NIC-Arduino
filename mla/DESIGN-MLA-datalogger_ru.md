## Зачем
Datalogger / ретранслятор LoRa принимает данные от **станций нескольких типов** (метео,
электричество, пчелиный улей, …) и должен записывать их в **один** `.mla`. v1.2 несёт
одну схему на файл (одна раскладка + множество идентичностей станций); формат datalogger
позволяет **каждой станции нести собственную раскладку столбцов**, по-прежнему разделяя
раскладку, если станции одинаковы.

## Модель — profile-ref
- **PROFILE** = раскладка столбцов (собственные дескрипторы полей данных).
- **STATION** = 8-байтная непрозрачная идентичность + 1-байтная ссылка на профиль.
- 1-байтный **индекс станции** в 16-байтной записи лога выбирает станцию →
  `{ identity, profile_ref }` → профиль → декодирование полезной нагрузки.

```
log record.index → STATION (identity + profile_ref) → PROFILE (column layout) → values
```

Так *раскладка* разделяется между одинаковыми станциями (8 метеостанций → 1 профиль
+ 8 строк станций), и при этом в одном файле допустимы *разные* раскладки (метео + электричество).

## Двоичная структура (передаётся в слоте `schema_table` префикса, после заголовка 34 B)
Каждая секция помечена тегом и сама задаёт свой размер; читатель обходит их по порядку. Весь
блоб покрыт CRC префикса — точно так же, как таблица схемы v1.2.

```
LOG       : 0x4C  n_log         n_log × 16B descriptor      (describes the fixed 16B record)
PROFILES  : 0x50  n_profiles    [ n_data(1B)  n_data × 16B ] × n_profiles
STATIONS  : 0x54  n_stations    [ identity(8B)  profile_ref(1B)  elevation(2B)  name(32B) ] × n_stations
```

`elevation` — метры со знаком в формате **i16 little-endian** (`0x8000` = неизвестно/не задано);
это ОТДЕЛЬНОЕ поле записи, расположенное после `profile_ref`, а не часть непрозрачной
идентичности. `name` — ОТДЕЛЬНАЯ человекочитаемая метка фиксированной длины 32 байта (UTF-8,
дополнение NUL, все нули = нет), расположенная последней, — материал для StationXML `<Site><Name>`;
это метаданные, записываемые **один раз в префиксе**, они НЕ передаются в каждой 16-байтной записи лога.
8-байтная идентичность здесь — ТА ЖЕ модель идентичности станции, которую теперь использует формат с единой схемой,
— это **унифицирует** идентичность станции на 8-байтной модели (старая
6-байтная запись region/number/reserved выведена из употребления).

16-байтный дескриптор поля и `physical = (raw + offset) × mantissa × 10^exp10` —
**те же**, что и в основном формате (`width 1/2/4 · unit · exp10 i8 · flags · offset i16 · mantissa i16 · name 8B`).
Теги (0x4C/0x50/0x54) отличаются от тега схемы (0x01), поэтому ядро
(`_schema_byte_len` в `nic_mla.py`) прозрачно определяет размер любого из форматов — `MlaCore`
просто переносит байты.

## Идентичность станции (8 B, непрозрачная)
MLA не придаёт этим 8 байтам никакого смысла; смысл придаёт glue. Кодировщики сборщика:
- `dl_gps(lat, lon)` — 2× i32 (градусы ×10⁷, ~1 cm)
- `dl_ident(number, region, kind, reserved)` — иерархическая (4× u16)
- `dl_raw(8 bytes)` — что угодно

**Стационарная станция → `dl_gps`, координаты снимаются один раз при установке.** Местоположение *и есть* идентичность
— никакого отдельного поля позиции, никакой схемы нумерации станций, из которой можно вырасти, глобальная уникальность с точностью до
~1 cm и готовность к пространственной индексации. Одна и та же 8-байтная идентичность служит любой входной части
(сейсмо, метео, ионо, …); зафиксируйте координату, чтобы она не «плавала» с каждым новым определением.
`dl_ident` / `dl_raw` остаются для иерархических или пользовательских ID.

> Четыре электросчётчика в одном шкафу → 4 станции с **одинаковым GPS, разным
> `number`, одинаковым profile_ref** (раскладка хранится один раз).

## Использование
```python
from mla_schema import MlaField
from mla_datalogger import DataloggerBuilder, DataloggerTables, dl_gps, export_csv
from nic_mla import MlaCore, MlaPosixHAL

# 1) describe profiles + stations
b = DataloggerBuilder()
b.log("datetime")
meteo = b.profile([MlaField("temp", 2, "degC", -2, signed=True),
                   MlaField("hum",  2, "pct",  -1)])
elec  = b.profile([MlaField("power", 2, "W"), MlaField("energy", 4, "kWh")])
b.station(dl_gps(50.0875, 14.4213), meteo)   # station 1
b.station(dl_gps(49.1951, 16.6068), meteo)   # station 2 (same layout)
b.station(dl_gps(50.0875, 14.4213), elec)    # station 3 (different layout)
blob = b.serialize()

# 2) write a real .mla (the tables ride in the schema_table slot)
hal = MlaPosixHAL.create("weather.mla", 64 * 1024)
with hal:
    m = MlaCore(hal); m.format(file_size=64 * 1024, schema_table=blob)
    t = DataloggerTables.parse(blob)
    m.append(1700000000, station=1, data=t.encode(1, {"temp": 25.45, "hum": 60.0}))
    m.append(1700000060, station=3, data=t.encode(3, {"power": 1500, "energy": 12345}))

# 3) export → one CSV / one SQL table per profile
export_csv("weather.mla", "out/")
```

## Ограничения
- ≤ 255 профилей, ≤ 255 станций (1-байтные счётчики / индекс), ≤ 255 столбцов на профиль.
- Полезная нагрузка данных на запись ≤ 65535 B (`length` в логе — u16); строки, сжатые DMD, ≤ 255 B.
- Файл имеет формат либо схемы v1.2, **либо** datalogger; они различаются по тегу по смещению 34.
  Контейнер, CRC, устойчивость к сбоям, ротация и сжатие идентичны v1.2.

## Что с чем связано
- `tools/mla_datalogger.py` — сборщик, читатель, декодирование по профилю, кодировщики идентичности, экспорт в CSV/SQL.
- `nic_mla.py` — `_schema_byte_len` определяет размер блоба datalogger (дополнение).
- Декодирование/экспорт со смешанными профилями проверены от начала до конца на реальном `.mla` в тестах.
